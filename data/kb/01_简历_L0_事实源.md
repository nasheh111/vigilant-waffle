### 项目二：质量分析报告助手（2024.12 - 2025.09）【校G：简历标题位写作"质量检验助手"】

**项目背景**：面向制造业质量分析场景，质量工程师在处理产线异常时，需要同时查询 MES、QMS、设备 PLC 日志、SPC 数据，并参考历史 8D 报告、FMEA、检验标准等文档。传统流程依赖人工汇总数据和编写报告，存在数据来源分散、缺陷描述不统一、历史案例难复用、报告编写周期长等问题。项目基于 RAG + Agent 构建质量问题诊断与报告生成助手，辅助完成相似案例检索、根因分析建议、报告初稿生成和人工审核提示。

**个人职责**：

1. **质量数据结构设计与多源数据接入**
   - 数据结构设计：主导设计质量问题标准化数据结构（QualityIssueRecord），覆盖缺陷类型、缺陷等级、发生时间、涉及产线/设备、批次号、责任工序、严重程度、是否重复发生等 15+ 核心字段；
   - 多源数据接入整合：主导将分散在 MES（生产执行）、QMS（质量管理系统）、设备 PLC 日志、SPC（统计过程控制）系统的质量数据进行整合汇聚，形成统一的质量数据视图，为 Agent 分析提供完整数据基础；
   - 质量问题知识库构建：参与基于 MinerU（RapidDoc）完成历史 8D 报告、FMEA（失效模式与影响分析）、质量检验标准、行业规范等 5000+ 页文档的解析入库，构建质量问题根因分析的知识基底，覆盖本厂近 3 年历史质量问题案例。

2. **质量问题诊断 Agent**
   - 根因分析 Agent：主导使用 LangGraph 编排根因分析流水线——当质量异常发生时，Agent 自动检索历史相似案例（通过 BGE-M3 混合检索），推荐最接近的历史问题及整改措施；同步查询 MES 系统，获取异常批次的工艺参数、原材料批次、设备状态、操作人员等关联数据，汇聚为分析上下文；调用 Qwen2.5-14B 综合案例库与实时数据，生成根因分析建议（如：最可能的失效模式、建议排查方向）；
   - 缺陷智能分类：主导针对一线人员缺陷描述不规范的问题，调用 Qwen2.5-14B 对缺陷描述进行标准化映射（如"产品表面有划痕" → 统一归类为"外观缺陷-划伤"），消除因描述差异导致的数据统计失真，并自动关联对应工序与根因模式。

3. **质量报告自动生成 Agent**
   - 报告模板解析：解析工厂现有 8D 报告、质量月报等 10+ 种报告模板，提取报告的结构框架（章节划分、必填字段、数据来源），建立报告模板库；
   - 报告内容生成：基于 LangGraph 编排报告生成，按模板定义的数据需求，从 MES/QMS 等多系统聚合相关质量数据（合格率、缺陷帕累托、SPC 异常点等），调用 Qwen2.5-14B 生成各章节分析内容；
   - 报告修改建议：参与在人工审核报告时，Agent 自动对比同类问题的历史报告，提示"本次分析是否遗漏了异常因素？是否存在类似案例？"等校验建议，帮助质量工程师查漏补缺；
   - 报告版本管理：基于 PostgreSQL 存储报告迭代历史，支持追溯修改记录，满足质量体系合规追溯要求。

**技术成果**：完成 5000+ 页质量文档的知识结构化，覆盖 FMEA、8D 报告、检验标准等 6 种格式，沉淀 800+ 条"问题-根因-措施"映射关系；RAG 检索 + 缺陷标准化分类后，历史案例召回率（Recall@5）从 68% 提升至 87%，缺陷描述自动归类准确率达 85%+，报告章节自动生成覆盖率达 70%+。

**业务成果**：在 2 条试点产线稳定运行 3 个月，质量问题根因定位时间从平均 4 小时缩短至 30 分钟以内，重复质量问题占比从 35% 降至 15%；8D 报告编制周期从 5 天压缩至 2 天，质量月报从 5 天缩短至半天，累计生成报告 15+ 份，已向全厂工程师全员培训。

**技术方案**：基于 Dify 内置 RAG 能力构建设备运维知识库，将设备手册、故障代码表、维修记录、操作规程等资料统一入库，通过文档解析、智能分段、Embedding 向量化和语义检索，实现"自然语言提问 → 知识库召回 → LLM 生成回答"的基础问答流程。系统支持维修人员通过 Web 端或 API 输入故障现象、设备型号、故障码等信息，快速检索相关资料并生成初步排查建议。

**个人职责**：

1. **Dify 平台选型与原型搭建**：负责 LLM + RAG 的技术方案设计，完成 Dify 平台选型、知识库配置与问答应用搭建，快速验证设备运维知识问答场景的可行性。
2. **多源文档入库与知识库建设**：负责设备手册、故障代码表、维修记录、操作规程等文档的整理、清洗与统一入库，支持 PDF、Word、Excel、TXT 等多种格式资料接入，并配置文档分段与向量化策略。
3. **检索参数与 Prompt 优化**：配置 Embedding 模型与知识库检索参数，调整分段长度、重叠窗口、Top-K 和相似度阈值；编写设备运维场景 Prompt，约束模型基于知识库回答，输出故障原因、排查步骤、处理建议和注意事项。
4. **问答流程发布与业务集成验证**：使用 Dify 工作流编排"用户提问 → 知识检索 → LLM 生成 → 答案输出"的基础流程，将应用发布为 Web 端及 API 接口，并完成企业微信集成验证，使一线人员可在聊天场景中进行故障查询。
5. **升级需求沉淀**：在试用过程中记录 Dify 原型在故障码精确匹配、复杂检索路由、证据校验、低置信度兜底、监控与部署可控性等方面的限制，为后续基于 LangGraph + FastAPI 自研升级提供需求依据。

**项目成果**：使用 Dify 快速完成设备运维 RAG 问答原型搭建，实现设备手册、故障代码表、维修记录等资料的统一入库和语义检索；初步打通"自然语言提问 → 文档召回 → LLM 生成回答 → Web/API 输出"的设备运维问答链路；完成企业微信集成验证，支持维修人员在聊天场景中查询设备资料和历史故障处理经验；验证了 RAG 在设备运维知识复用场景中的业务可行性，为后续自研系统升级明确了检索精度、流程可控性、证据校验和工程化部署方向。
