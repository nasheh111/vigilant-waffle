# AIGC 基于多 Agent 编排的智能视频生成平台 - 面试问答版

## 参考项目名称

- 基于多 Agent 编排的智能视频生成平台
- 从剧本到成片的多 Agent 协作视频生产平台
- 基于 LangGraph 的多 Agent 智能视频创作平台
- AI 智能导演

## 一句话介绍

这是一个多 Agent 协作的视频生成平台。用户输入一句话主题、基础剧本或参考文章，系统自动完成剧本创作、分镜设计、素材生成、配音、剪辑、质检和交付，最终产出一条可预览、可下载、可分享的视频。

我在项目中重点负责多 Agent 流程编排、任务状态设计、分镜 JSON 结构、异步任务队列、素材资产复用和质检返工机制。整体思路是用“导演 Agent + 专业执行 Agent”的方式，把视频生产从不可控的一次性生成，拆成可追踪、可重试、可评估的工程流程。

## 面试官：这个项目解决什么问题？

回答口径：

它主要解决 AIGC 视频生成链路长、结果不可控、返工成本高的问题。

传统做法是用户输入一句 Prompt，直接调用视频模型生成，结果经常出现剧情不连贯、角色不一致、时长对不上、配音和画面不同步、事实内容编造等问题。而视频生产又不是一个单点任务，它包含编剧、分镜、美术、配音、剪辑、质检多个环节。

所以我把它设计成多 Agent 协作平台。主编排 Agent 像导演，负责任务规划、预算控制、状态调度和冲突仲裁；下面有编剧、分镜、美术、配音、剪辑、质检等专业 Agent，各自处理自己的任务。这样每一步都能记录、校验和返工。

## 面试官：你具体是怎么做的？

回答口径：

我先把视频生产链路拆成一张 DAG，而不是串成一个超长 Prompt。

流程是：

1. 输入解析：判断用户输入是一句话主题、已有剧本，还是参考文章。
2. 知识入库：如果有参考文章，就做切片、向量化和摘要，后面剧本生成时用 RAG 注入事实依据。
3. 剧本生成：编剧 Agent 输出结构化剧本，包括场景、旁白、字幕、人物和预估时长。
4. 分镜生成：分镜 Agent 根据旁白意群拆镜头，输出每个镜头的画面 Prompt、镜头时长、景别、运镜、转场和资产 ID。
5. 并行生成素材：美术 Agent 生成画面/视频片段，配音 Agent 生成旁白、角色音色和背景音乐。
6. 剪辑合成：剪辑 Agent 用 FFmpeg 按时间轴合成，烧录字幕，做转场和导出。
7. 质检返工：质检 Agent 检查音画同步、角色一致性、事实一致性、安全合规和清晰度，不通过就定向返工。

技术上我会用 LangGraph 做流程编排，用 Redis/Celery 做异步任务，用 MinIO 存素材，用 MySQL 记录任务和资产元数据，用向量库做知识和素材检索。

## 面试官：为什么要用多 Agent，而不是一个 Agent 全部做完？

回答口径：

因为视频生成链路太长，一个 Agent 全部做会有三个问题。

第一，上下文太大。剧本、分镜、素材、音频、剪辑参数都放进一个上下文，很容易丢信息。

第二，职责不清。生成失败时不知道是剧本问题、分镜问题、画面问题还是剪辑问题，排查成本高。

第三，不能并行。画面生成和配音本来可以同时跑，如果一个 Agent 串行执行，整体耗时会很长。

多 Agent 拆分后，每个 Agent 的输入输出都更清楚，失败能定位，画面和配音也能并行执行。主编排 Agent 负责全局协调，不直接生成具体内容。

## 面试官：主编排 Agent 做什么？

回答口径：

主编排 Agent 的角色类似导演，主要做四件事。

第一是任务规划。它把用户目标拆成剧本、分镜、素材、配音、剪辑、质检这些子任务，并判断哪些串行、哪些并行。

第二是预算和配额控制。比如用户只要 30 秒短视频，就限制镜头数量、模型档位和最大重试次数，防止成本失控。

第三是状态调度。每个子 Agent 完成后都会回写状态，主编排 Agent 根据状态推进下一步。

第四是仲裁。比如质检认为某个镜头画面不一致，主编排 Agent 判断应该返工美术 Agent，还是调整分镜 Prompt。

## 面试官：分镜 JSON 为什么重要？

回答口径：

分镜 JSON 是整个系统的中枢数据结构。

视频生成最怕每个环节各说各话。编剧输出一段自然语言，画面模型、配音模型、剪辑工具如果各自理解，就很容易出错。所以我把分镜设计成结构化 JSON，每个镜头都有固定字段：

- `shot_id`：镜头 ID
- `duration`：镜头时长
- `voiceover`：旁白
- `subtitle`：字幕
- `visual_prompt`：画面 Prompt
- `camera`：景别、运镜
- `transition`：转场
- `character_id`：人物资产 ID
- `scene_id`：场景资产 ID
- `asset_refs`：需要复用的素材

后面的美术、配音、剪辑、质检 Agent 都围绕这份 JSON 工作，这样可以减少歧义，也方便断点续跑。

## 面试官：音画同步怎么保证？

回答口径：

我把音画同步提前到剧本和分镜阶段解决，而不是等剪辑阶段硬修。

具体做法是“旁白时长驱动镜头时长”。编剧 Agent 生成旁白后，先按语速估算时长，比如每分钟多少字，再给每个镜头分配基准时长。分镜 Agent 按旁白意群切分镜头，配音 Agent 生成 TTS 后再返回真实音频时长，剪辑 Agent 根据真实时长微调画面片段和字幕时间轴。

如果音频时长偏差过大，系统会优先让编剧 Agent 缩短或扩写旁白，而不是让剪辑 Agent 强行拉伸视频。

## 面试官：怎么保证角色和画面一致性？

回答口径：

我主要靠资产 ID 和参考图复用。

如果每个镜头都重新用自然语言描述角色，比如“一个穿蓝色衣服的年轻人”，模型每次生成都可能不一样。所以系统会先建立人物库和场景库，人物包括角色档案、定妆照、服装、发型、音色 ID；场景包括色调、空间设定、参考图和历史素材。

分镜里不只是写文字描述，而是引用 `character_id` 和 `scene_id`。美术 Agent 生成画面时优先读取这些资产和参考图，素材生成后也回写资产库。这样角色外观、场景色调、镜头风格会更稳定。

## 面试官：RAG 在视频项目里怎么用？

回答口径：

RAG 有两个方向。

第一个是生成前注入事实。用户如果输入参考文章或产品资料，系统会把资料切片入库，剧本 Agent 生成时检索相关片段，避免编造事实。

第二个是生成后回查。质检 Agent 会把剧本、字幕或旁白里的关键事实再拿回知识库检索，看是否有依据。如果没有依据，就标记为事实风险，返回给编剧 Agent 修改。

所以 RAG 在这里不是简单问答，而是给视频内容提供事实约束。

## 面试官：异步任务是怎么设计的？

回答口径：

视频生成是分钟级任务，不适合用同步 HTTP 请求一直等结果，所以我会设计成异步任务。

前端提交任务后，后端生成 `task_id`，把任务写入数据库，并投递到 Celery/Redis 队列。前端通过轮询或 WebSocket 订阅任务状态，比如 `pending`、`script_running`、`shot_running`、`asset_running`、`editing`、`reviewing`、`finished`、`failed`。

每个 Agent 执行完一个节点，就把结果和状态写回数据库。这样用户可以看到进度，也可以取消、重试或下载中间版本。

## 面试官：质检和返工怎么做？

回答口径：

质检 Agent 会输出结构化评审结果，不只是打一个分。

它主要检查五类问题：画面和分镜是否匹配，字幕/旁白是否和剧本一致，音画是否同步，事实是否有依据，角色和场景是否一致。

如果不通过，质检结果会带上错误类型和责任节点，比如 `script_fact_error` 回到编剧 Agent，`character_inconsistent` 回到美术 Agent，`audio_mismatch` 回到配音或剪辑 Agent，`subtitle_overflow` 回到剪辑 Agent。

返工最多 3 次，超过就转人工审核，防止系统无限循环烧钱。

## 面试官：这个项目最大的难点是什么？

回答口径：

最大的难点是长链路任务的可控性。

一个视频从文本到成片，任何环节出错都会影响最终效果。如果只是端到端生成，出了问题很难定位。所以我把链路拆成节点，把每个节点的输入、输出、状态、错误类型都结构化保存。

另一个难点是一致性，尤其是角色一致、场景一致、音画同步。我用资产 ID、分镜 JSON、旁白时长驱动和质检返工机制来控制这些问题。

## 面试官：怎么降低成本和耗时？

回答口径：

成本和耗时主要从四方面优化。

第一，能并行的并行。剧本和分镜必须串行，但画面生成和配音可以并行。

第二，素材缓存。人物定妆照、场景参考图、历史片段可以复用，不需要每次都重新生成。

第三，模型分级。脚本摘要、敏感词检查、结构化提取用轻量模型，关键画面生成才用高成本模型。

第四，定向返工。质检失败时只重做对应镜头或对应节点，不重跑整条视频链路。

## 面试官：如果线上任务失败，你怎么排查？

回答口径：

我会按 `task_id` 回放整条链路。

先看任务状态卡在哪个节点，再看这个节点的输入、模型参数、输出、错误日志和质检意见。如果是模型服务超时，检查模型网关和重试策略；如果是 JSON 解析失败，检查 Prompt 约束和 Schema 校验；如果是素材生成失败，检查素材服务返回；如果是 FFmpeg 合成失败，检查时间轴、素材路径和编码参数。

因为每个节点都有状态和产物记录，所以排查时不是靠猜，而是按链路定位。

## 面试官：项目可以量化哪些指标？

回答口径：

可以分成效果指标、效率指标和稳定性指标。

效果指标：剧本通过率、分镜可用率、角色一致性评分、音画同步通过率、事实回查通过率。

效率指标：平均生成时长、单条视频人工修改次数、一次成片通过率、素材复用率。

稳定性指标：任务成功率、平均重试次数、模型调用失败率、单任务成本、队列等待时间。

如果是 MVP 阶段，我会重点看任务成功率、一次成片通过率、平均生成时长和单任务成本。

## 面试官：如果继续优化，你会怎么做？

回答口径：

我会优先优化三块。

第一是更强的一致性控制，比如固定角色参考图、LoRA 风格资产、镜头级一致性评分。

第二是交互式修改。用户可以只修改某个镜头、某句旁白或某段字幕，系统只局部重生成。

第三是投放反馈闭环。如果视频用于营销，可以把完播率、点击率、转化率回流到脚本和分镜策略里，形成数据驱动的创作优化。

## 30 秒项目总结

这个项目是一个从主题到成片的多 Agent 视频生成平台。它用主编排 Agent 做导演，拆解和调度编剧、分镜、美术、配音、剪辑、质检等专业 Agent；用分镜 JSON 作为中枢数据结构，用资产 ID 和参考图解决一致性，用异步任务队列支撑分钟级生成，用质检返工闭环保证结果可控。它的核心不是简单生成视频，而是把 AIGC 视频生产做成一个可追踪、可重试、可交付的工程系统。
